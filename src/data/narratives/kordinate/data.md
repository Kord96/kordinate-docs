# Data {#agent-memory}

## Where Does Truth Live?

Kordinate's state is distributed across five stores, each chosen for a specific reason. There is no database — everything is files on disk, versioned by git, readable by both humans and agents.

## Agent Memory {#agent-memory-store}

The most important store is **Agent Memory**: markdown files with YAML frontmatter, organized by agent under `agents/<name>/memory/`. Each file has a `preloaded` property that determines when it is loaded — on boot, on demand, or never. Memory is typed: `user` (who the developer is), `feedback` (how to approach work), `project` (ongoing context), and `reference` (pointers to external systems).

Memory files are the institutional knowledge layer. When a developer says "don't mock the database in these tests," **Scribe** writes a feedback memory that persists across conversations. The next time any agent considers writing a test, that memory is in its context. The choice of markdown over a database was deliberate: markdown is human-auditable, git-diffable, and readable by agents without any driver or API. The tradeoff is that memory search is linear (no indexing), but the `preloaded` flag keeps the working set small — typically 4-5 files loaded on boot, with the rest available on demand.

The `MEMORY.md` file in each agent's dynamic directory is a generated artifact, not a source of truth. The **Agent Memory Hook** rebuilds it from shared memory, instructions, static knowledge, and kord discovery. If it becomes corrupted, deleting it and spawning the agent again regenerates it cleanly.

## Kord Response Cache {#kord-cache}

**Beorn** stores kord responses as `data-<slug>.md` files alongside the contract. Each cached response is paired with a `.snapshot` file containing md5 hashes and line counts of all input files at the time the response was generated. This snapshot powers the magnitude-based expiry: instead of asking "is this cache old?" the system asks "how much has the world changed since this cache was built?"

The cache is per-project: a kord like `project-analysis` produces `data-stoik.md`, `data-logbd.md`, etc. This means analyzing one project does not invalidate the cache for another. The snapshot approach means that touching a comment in one file does not trigger a full re-analysis — only changes proportional to the project size cross the staleness threshold.

Cache files are not versioned by git. They are ephemeral artifacts that can be regenerated by re-running the kord. If the workstation pod restarts, caches are lost (they live on the pod filesystem, not a PVC), and the next kord invocation rebuilds them.

## Centralized Configuration {#config-store}

**Config YAML** is the single source of truth for all infrastructure coordinates: cluster IPs, service ports, namespace layouts, Cloudflare tunnel IDs, Tailscale network addresses. Every deployment manifest, monitoring configuration, and connection string references this file rather than hardcoding values. **Alfred** is the primary writer, but the field-level ACL in `config-acl.yaml` allows other agents to own specific sections — **Deployer** owns cluster topology, **Sauron** owns monitoring endpoints.

The configuration ships with placeholder values. After installation, the developer fills in their actual infrastructure details and runs `git update-index --assume-unchanged` to prevent local edits from appearing in git status. This keeps the development repo clean while allowing each installation to have its own configuration.

## KORD.json Registry {#kord-registry}

The **KORD.json Registry** is the auto-generated manifest of everything in the system. Each entry has a `path`, `description`, and metadata flags: `curated` (protected by the **Guard Hook**), `preloaded` (loaded on boot), `scope` (global or project). The registry powers three systems: the guard hook uses `curated` to decide what needs scribe authentication, **Beorn** uses agent entries for discovery, and the **Boot Skill** uses `preloaded` to decide what to load.

The registry is derived, not authoritative — it is regenerated from frontmatter in the source files. If it becomes stale, re-running the generator (part of the install/onboard process) rebuilds it. The guard hook's KORD.json check is a performance optimization: instead of reading frontmatter from each file on every write operation, it reads the pre-computed registry.

## Authentication Locks {#auth-locks}

The simplest store is the authentication lock system: static files at `profile/locks/<agent>` and ephemeral copies at `/tmp/.<agent>-auth`. The lock file content is a shared secret — the guard compares the two files to verify authentication. Locks are copied on `/authenticate` and removed when the task completes.

This is intentionally ephemeral. If the pod restarts, all `/tmp/` files are cleared, and no agent is authenticated — which is the safe default. The static lock files in `profile/locks/` persist because they are part of the kordinate package, but they are never sensitive (they are just random tokens used for comparison, not credentials). The actual credentials live in the **Pass Credential Store** — a GPG-encrypted password manager that is external to kordinate entirely. Kordinate's credential protocol mandates that all secrets go through `pass`, never hardcoded in manifests or configuration files.
